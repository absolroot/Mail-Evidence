# MSG 화면과 조사 흐름 검수

2026년 11월 23일. 실제 MSG를 검색하고, 저장된 전송 헤더와 첨부 원본을 확인하고, 필요한 자료를 내보낸 뒤 결과를 재검증하고 검색으로 돌아왔다. 일반 사용자 권한의 격리된 Windows 데스크톱에서 Release WPF 창을 열고 제품의 버튼과 키 이벤트를 실행했다. 원본 헤더와 첨부의 바이트 기준은 제품 엔진과 별도의 CFB 판독으로 만들었다. [MSG 엔진 검증](msg-verification.md)

## NTFS Tracer를 기준으로 적용한 부분

NTFS Tracer의 `CompactMenu.xaml`을 공유했다. 메뉴 기준 높이는 25 DIP이며 목록 행은 23 DIP, 머리글은 26 DIP다. 조사 목록 위에 검색과 내보내기를 배치하고 하단 근거 영역에서는 같은 메시지의 탭을 전환할 수 있게 했다. 메일에서 반복해서 확인하는 대상인 전송 헤더, 첨부, 원본 바이트를 하단 탭으로 연결했다. |---|---|

| 파일 시작과 CFB 첨부 스트림의 시작 위치를 혼동할 수 있다. | PDF 스트림의 오프셋 0에서 `%PDF-`, 전체 MSG 파일의 오프셋 0에서 `D0 CF 11 E0`를 확인했다. 파일 보기로 전환하면 스트림 경로가 사라졌다. 첨부 스트림 화면 |
| 첨부 목록과 상세에 긴 경로를 반복하며 저장할 형식은 하나뿐인데 선택 상자가 나온다. | 목록의 저장 형태에서 데이터 스트림과 중첩 저장소를 구분했다. 선택 상세에서 한 번만 전체 경로·태그·해시를 표시했다. 첨부 이름으로 찾으면 일치한 첨부가 먼저 선택됐고, 첨부 저장의 형식 선택 상자는 나타나지 않았다. 첨부 화면 |

## 판독한 바이트와 저장 결과

- Tika ANSI MSG를 제목으로 찾아 `0x007D001E`의 `Date`를 열었다. 스트림 상대 위치와 표시한 바이트는 독립 판독값과 일치했다. POI Unicode MSG에서는 `0x007D001F`의 `Received`를 같은 방식으로 대조했다. ANSI 원본 화면 · Unicode 원본 화면
- POI PDF의 `0x37010102` 화면에 표시한 첫 4,096바이트와 저장한 전체 13,539바이트를 독립 판독값과 비교했다. 저장 후 재검증했고, 매니페스트에 CFB 저장소 경로와 MAPI 태그가 남았다. 중첩 저장소의 위치를 표시하며 해당 객체의 독립 파일 저장을 제공하지 않는다. 중첩 저장소 화면 · 첨부 재검증 화면
- 전체 MSG 사본은 원본 CFB 파일과 바이트 및 SHA-256이 일치했다. 추출과 저장 전후의 두 입력 SHA-256도 같다. 원본 재검증 · 검색 복귀

밝은 테마와 어두운 테마에서 위 흐름을 통과했다. 기존 EML·MBOX 화면 시험도 재실행했다. 격리된 WPF에서 논리 포커스와 키 이벤트를 검증했으며 실제 사용자 과업 시간은 측정하지 않았다. Windows x64 1.1.0 자체 포함 배포판은 POI MSG를 인수로 전달해 시작 창이 뜨는 것을 별도로 확인했다. 밝은 테마 기록 · 어두운 테마 기록 · EML·MBOX 회귀 · 콘솔 15건 · 실행 파일 검증
