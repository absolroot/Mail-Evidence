# 구형·블록 인코딩 OST 화면 검수

2026년 11월 23일 Mail Viewer 1.4.0 Release를 별도의 Windows 데스크톱에서 실행했다. 밝은 테마와 어두운 테마에서 Aspose가 공개한 실제 OST를 열었다. 검수 전에 파일 헤더 `SO`, Unicode 23, 512바이트 페이지, 블록 인코딩 `0x01`과 파일 SHA-256을 대조했다. [공개 원본](https://github.com/aspose-email/Aspose.Email-for-.NET/blob/88cb2da311382bbbba6d14813127b0e6b3854c12/Examples/Data/MAPI/SampleOstFile.ost) · 어두운 테마 실행 결과 · 밝은 테마 실행 결과

| 조사 단계 | 확인한 동작 |
|---|---|
| 자료 열기 | 내장 항목이나 파일 데이터가 없는 첨부에서 판독 범위 제한이 표시됐다. 확인창에서 읽은 범위를 적용하고, 자료 탭에서 형식·페이지 크기·블록 인코딩과 원본 SHA-256을 확인했다. 일반 메일 81건이 열렸다. 일부 판독 확인 · 자료 화면 |
| 폴더와 검색 | `Root - Mailbox → IPM_SUBTREE → Inbox`를 열었다. `Inbox` NID `0x00002182`의 일반 메일은 11건이었다. 제목에 `newsletter copy`를 입력하자 `newsletter copy`와 `RTF newsletter copy`가 표시됐다. 화면에서 메시지 NID `0x00214D84`를 가진 행을 선택했다. 폴더 화면 |
| 전송 헤더 대조 | 헤더 19행의 순서를 대조했다. `Received` 행에 표시된 338바이트를 독립 판독 값과 대조하고, **블록 디코딩 후** 속성 상대 오프셋임을 확인했다. 영어로 전환한 뒤에도 선택·범위·바이트가 같았다. `Esc`를 누르자 같은 헤더 행으로 돌아갔다. 헤더 Hex · 영어 화면 |
| 첨부 대조 | `image001.jpg`를 선택해 첨부 NID `0x000082A5`, MAPI 태그 `0x37010102`와 길이 20,833바이트를 확인했다. Hex의 첫 구간을 독립 판독과 대조했고, 화면에 표시된 첫 페이지와 저장 파일의 같은 구간도 대조했다. `Esc`로 해당 첨부로 돌아갔다. 첨부 Hex |
| 내보내기와 결과 검증 | 선택한 메일을 JSON과 1,872바이트 전송 헤더 속성 `.bin`으로, 선택 첨부를 JPG로 저장했다. 앱에서 두 묶음을 다시 검증했다. 저장한 헤더와 첨부의 전체 SHA-256은 각각 독립 판독과 일치했다. 매니페스트 두 개에 입력 SHA-256, 레이아웃, 폴더·메시지 NID와 속성 태그가 남았다. 전송 헤더 결과 · 첨부 결과 |
| 검색 복귀 | 두 내보내기 결과에서 기존 폴더, 검색어, 결과 2건, 선택 행, 키보드 포커스로 돌아왔다. 결과 표에서 `Enter`로 같은 메일의 근거를 다시 열었다. 780×600 DIP 창에서도 검색과 선택 상태를 확인했다. 복귀 화면 |

별도 입력 검수에서 정상 Unicode 36 OST를 연 상태로 새 자료 분석을 취소하고, 기존 결과 2건이 유지되는 것을 확인했다. 언어를 바꾼 뒤에도 미적용 자료의 진단이 남았다. 다시 분석하고 일부 판독을 수락하자 구형 OST의 일반 메일 81건이 적용됐다. 이때 지원하지 않는 버전은 검증용으로 만든 사본을 사용했다. 입력 진단 검수

기존 조사 화면 회귀에서 PST, Unicode 36 OST, MSG, EML·MBOX의 검색부터 원본·산출물 대조와 복귀까지 다시 확인했다. 배포 폴더의 Windows x64 실행 파일에는 .NET 런타임이 함께 있으며, 구형 OST 경로를 인수로 전달해 제품 창이 열리는 것을 확인했다. PST 회귀 · 기존 OST 회귀 · MSG 회귀 · EML·MBOX 회귀 · 배포 실행 확인
