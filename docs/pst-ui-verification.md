# PST 화면과 조사 흐름 검수

2026년 11월 23일. 별도 Windows 데스크톱에서 Release WPF 화면을 열고 실제 두 PST를 선택했다. 폴더 탐색, 검색, 원본 속성 대조, 내보내기, 결과 재검증과 복귀에 연결된 화면 동작을 실행했다. 바이트와 NID를 비교할 독립 기준은 배포된 다른 PST 판독기로 만들었다. [독립 기준과 엔진 검증](pst-verification.md)

## 화면과 조사 범위

NTFS Tracer의 목록 가까이에 검색과 적용 범위를 놓고, 하단에서 선택한 기록의 근거를 확인하는 구성을 유지했다. PST 폴더 탐색은 결과 목록 옆에 배치하고 하단에 헤더와 첨부의 작업 공간을 확보했다. [참조 화면](https://github.com/absolroot/NTFS-Tracer/blob/main/docs/media/file-history-dark.png) · 팀의 독립 반례 기록

| 검토에서 발견한 문제 | 반영 후 실물 시험 |
|---|---|
| 폴더를 해제하면 다른 PST의 결과까지 붙는다. | Inbox 1건, 같은 PST 전체 2건, 두 PST 전체 8건을 구별했다. 상위 폴더에서 하위 포함을 켜기 전에는 0건이었고 켜면 두 폴더의 결과가 표시됐다. |
| 다른 원본을 골랐지만 아직 검색을 적용하지 않은 상태에서 이전 결과를 저장할 수 있다. | 미적용 원본이 표시됐고 적용 전 이전 선택·검색 결과를 저장하는 명령이 비활성화됐다. 폴더를 오갈 때 입력 중인 검색어는 그대로였고, 마지막으로 적용한 검색이 폴더 범위에 맞게 갱신됐다. |
| 제목과 첨부 이름이 같은 메일을 구분하기 어렵다. | libpff 공개 자료의 두 결과가 서로 다른 PST 폴더로 표시됐다. Inbox의 결과만 골라 저장하고 매니페스트에서 소스 해시·폴더 NID·메시지 NID를 대조했다. 동명 결과 |
| 같은 NID를 다른 PST에서도 사용할 수 있고, 논리 위치를 파일 오프셋으로 오독할 수 있다. | 두 PST의 동일한 메시지 NID가 별개 결과를 가리켰다. 원본 속성 화면에는 PST 출처, 폴더·메시지·첨부의 NID와 태그가 연결됐다. 원본 위치 복사에 파일 경로와 SHA-256을 포함했다. |
| 좁은 창에서 적용 폴더나 펼친 트리 토글을 알아보기 어렵다. | 780×600 DIP에서 적용 범위에 PST 파일명과 Inbox가 표시됐다. 긴 경로는 도구 설명에 남겼다. 밝은 테마와 어두운 테마에서 폴더 탐색과 첨부 확인을 검수했다. 트리를 접고도 Inbox와 선택한 메시지를 유지했다. 좁은 창 · 트리 접기 |

## 원본과 내보낸 결과 대조

- Tika의 폴더를 선택하고 제목으로 `Re: Feature Generators`를 찾았다. 메시지 NID `0x00200024`의 `0x007D001F`에 있는 전송 헤더는 10,660바이트이며 `Received`가 10줄이다. 화면에서 첫 `Received` 필드의 상대 위치와 Hex를 대조했다. PST 메시지 근거로 저장한 헤더 속성 전체가 독립 판독값과 같았다. 원본 헤더 · 저장 결과 재검증
- libpff 공개 자료에서 Inbox를 선택하고 첨부 이름 `1.jpg`로 찾았다. 저장된 전송 헤더가 없는 상태를 표시했다. 첨부 NID `0x00008025`의 `0x37010102`에서 읽은 JPEG 1,969바이트와 화면 Hex, 저장 파일이 독립 판독값과 일치했다. 첨부 속성 · 첨부 재검증
- 저장 후 **검색 결과로 돌아가기**를 누르자 두 작업 모두 같은 PST, 폴더, 검색어와 선택 행을 복원했다. WPF의 논리 포커스와 `Enter` 이벤트로 Tika의 같은 메시지 헤더를 다시 열었다. 입력 두 파일의 전체 SHA-256은 시험 전후 같았다. 검색 복귀
